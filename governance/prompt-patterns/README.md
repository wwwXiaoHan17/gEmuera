# 用户常用提示词模式库

收集用户（开发者）在任务中反复出现的提示词结构，Agent 识别模式后按对应策略输出，
减少来回确认、提高一次通过率。来源：任务会话 + git 提交历史归纳。

## 模式速查表

| # | 模式名 | 特征（用户怎么说的） | 应对策略 |
|---|--------|---------------------|---------|
| 1 | 验证检查型 | "检查 X 在 Y 平台是否能正常…"、"确认…是否可用" | 先静态审查平台分支（OS.GetName/HasFeature 门控），再给出结论 + 证据（文件:行）；无法实测时明确标注"需实测项" |
| 2 | 设计设想型 | "我设想的是…"、"我的想法是…" | 优先实现用户设想本身，同时保留原功能语义；把用户设想翻译成具体技术方案时给出决策与 Why |
| 3 | 对齐型 | "对照参考源码"、"减少功能偏移"、"语义对齐" | 修改/优化前对照 `E:\MyCode\Era\emuera.em-master`（v24）或 `emuera_lazyloading_*`（snake），在代码注释里写明对照点 |
| 4 | 审查型 | "检查当前项目是否需要对代码、结构、性能进行优化" | 三维检查（代码质量/结构/性能），按严重度输出问题清单 + 性价比排序建议；不硬凑问题 |
| 5 | 自我进化型 | "实现自我更新/自我进化"、"收集常用提示词" | 任务完成后写 `governance/evolution-log/` 复盘、更新本提示词库、必要时更新 AGENTS.md |
| 6 | 平台双轨型 | 问题同时涉及"移动端/桌面端" | Android 结论必须以 APK 实测为准，桌面仅调试；移动端与桌面分支分别给出行为差异说明 |
| 7 | 改动保护型 | "注意未提交改动"、"避免冲突" | 动手前先 `git status` 识别未提交工作，在其基础上迭代，不覆盖他人/上次会话的成果 |
| 8 | 规范/提示词强化型 | "X 的描述太简略"、"需要加强一下提示词"、"写得太松/不够强制" | 不只补一句"请遵守"：补「触发判据 + 可判定的验收标准 + 红线反例 + 带证据位置的自检清单」四件套；明确权威口径（冲突以谁为准）并收敛旧表述；改规范类提示词时同步写 evolution-log 并按新标准自检 |
| 9 | 插件/组件增强型 | "优化这个 X 插件/组件，补全语法和样式，>、表格、图片等确实的功能"（点名路径或 skill + 列举缺失项） | 先实测目标运行时能力（如 RichTextLabel BBCode 支持、版本门控）再写契约规格；保留原公开 API 与目录可整体替换性（第三方 addon 不覆盖 LICENSE/致谢）；补无头契约测试 + 窗口模式截图验证；README/CHANGELOG/示例同步，交付时列出新增属性、限制与升级说明 |
| 10 | 参考实现裁决型 | "X 和 Y 的 API 好像一样？"、"X 和 Y 有什么区别吗？"、"uEmuera/XEmuera 是如何实现 X 的"、"加回来，并且按照 x/uEmuera 的实现" | 用户质疑两个功能是否重复、或问参考实现怎么做时，先给出参考实现（XEmuera/uEmuera/原版 Emuera）里两者的**语义分工对照**并等用户裁决，不要先删/先合并再补救；裁定后各链路保持独立（界面缩放 / 字号排版级 / 缩放板内容层三条 API 勿合并）。先例：`evolution-log/2026-11-16-ui-scale-setting.md` 2026-11-20 的三条补遗（字号滑条删除 → 按 XEmuera 加回 → 「API 不要搞一起」） |
| 11 | 只发图 + 极简接力型 | 消息里只有一张截图、没有文字；之后用几个字的祈使句推进："D:\clone"、"重新盘点，并向上更新"、"继续"（可连续多次）、"压缩上下文再继续"；对记账用一句话裁定："没有实质上的变化，所以不纳入上传" | 只发图时：先问一次意图，没回答就按推荐的只读评估推进；贴图缓存长边被压到 2000px，长图先切块放大再读，小字里的标识符（项目名、关键字）放大确认前只能当假设。极简接力时：一口气做到底，不要在里程碑处停下来汇报等待；被挡住时选合理默认并说明，不反复确认；用户说「继续」就接着做，不重述已完成的部分。记账范围听用户一句话裁定（无实质改动就不写 evolution-log / backlog）。先例：`evolution-log/2026-11-24-snake-18.0-alignment.md`（同一会话里从截图评估 → 克隆 → 重新盘点 → 向上更新） |
| 12 | 引用批注追问 → 环境反驳 → 放行型 | 用引用批注在我的某句结论上问"怎么做呢？"（不是开工指令）；听完方案后先抛出基于自己环境的反驳——"但是内置包我也用不了啊"；之后才用"自愈方案实现看看"放行 | 批注提问 = 要设计讲解：给做法、边界、需要用户裁定的取舍、工作量，讲完等，不要顺手开写。环境反驳先当事实对待，不争辩也不照单全收——用实测验证前提（模拟器 / 无头跑一轮比讨论有效），前提属实就改方案，前提不属实就用证据说明并保留方案。"X 实现看看"才是开工信号。先例：`evolution-log/2026-11-24-stale-first-party-pack-self-heal.md`（"内置包用不了"实为「手动放过的包被当成用户文件永不更新」，实测后确认自愈方案成立） |
| 13 | 隔天后的「核对一遍」型 | 任务交付（甚至已经提交）一两天后只说"核对一遍"，不指明范围 | 先从磁盘状态起算，不沿用上次的结论：`git log` / `git status` 看这两天用户或别的会话做了什么（提交、复审修正），以当前提交为基准重跑构建与门禁；另起一个只读代理从头审一遍提交（自审有盲区——实测它找到了 3 条我没想到的边界缺陷）；上次只做了静态验证的修正一律补运行验证；进化记录里的可量化陈述（用例数、证据路径）逐条对一遍，错的在补遗里更正、不回改；环境类失败（如 Gradle 缓存损坏）查清范围后绕行，不动用户的全局环境，但要把修法明确告诉用户。先例：`evolution-log/2026-11-24-stale-first-party-pack-self-heal.md` 补遗（2026-11-26） |

## 使用方式

- 会话开始时（读完 AGENTS.md 后）快速浏览本表，确认本次任务命中的模式。
- 任务执行中若发现新模式或新模式变体，任务结束时补充到表中。
- 模式库只增不改历史行（修正以追加方式记录）。

## 用户任务风格备注（git 提交历史归纳）

- 提交信息：conventional commits（`feat:/fix:/perf:/docs:/chore:`）+ 中文详细描述。
- 高频主题：性能优化（渲染/输入/启动）、组件化重构、平台适配（Android 优先）、
  功能对齐（对照参考源码）、UI 深色主题统一、i18n 语言文件同步。
- 语言文件改动规律：改 4 个文件（zh_cn / en_us / jp / default）同步更新。
- 提交粒度（2026-11-23 用户指示「下次不要搞这么多提交，能一次解决就一次解决」）：同一轮收尾 / 记账的
  文档改动合成一次提交——动手前先把事实查全（PR 状态、未合并提交清单、用户裁定）再一次成稿；PR 创建后的
  记账攒到下一个自然节点一起提交，不要出现「创建 PR → 记账提交 → 合并 → 闭环提交」的连环小提交。
