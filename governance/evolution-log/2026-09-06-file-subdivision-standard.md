# 文件细分与规模标准制定（file-subdivision-standard）

## 任务目标与成果

新建 `FILE_STANDARD.md`（文件规模阈值、三种拆分模式、命名约定、存量触碰迁移策略、六类钉扎机制硬约束、按范围分流的验证清单），并在 `AGENTS.md` 文件管理规范追加第 6 条挂接。数据基线 `451ea19`（2026-08-22）。

## 关键决策与 Why

1. **"只减不增 + 触碰迁移"替代专项大重构**：>2000 行文件禁止净增（50 行/PR 容差 + hotfix 豁免 + merge-base 基线定义），拆分只在任务触碰且功能域 ≥200 行可干净切出时进行。理由：符合项目"不为重构而重构"原则，且消除了紧急 hotfix 与规则死锁。
2. **钉扎清单不搞手工枚举，以 catalog 文件 + 四条 grep 流程为准**：手工枚举在首轮草案里就错了两处（漏 EmueraContent.cs 这个 marker 分类文件、Config 计数错），证明枚举必然过时；§6 开头给出可直接执行的检查命令。
3. **六类钉扎/链接机制全部写入硬约束**：方言证据链（字节级哈希+fileRegex）、snake-alignment 路径正则（约 20 文件）、save-baseline SHA+字面量、legacy-runner 契约测试（已因 M0 改名静默损坏过——实证此风险真实）、tools 三工程显式 `<Compile Include>`（不在 sln 内，主构建覆盖不到，坏了是静默的）、.tscn 无 uid 硬路径/preload。拆分任何 §5 清单文件几乎必然命中其中 2-3 类。
4. **FunctionIdentifier.cs / Creator.cs 禁止移动注册行**（生成器单声明约束 + 文本正则钉扎，移动即 exit 1），这两个文件只允许原地修改。

## AI 表现复盘

- **有效**："遗漏猎手"审查角度价值极高——发现了草案完全遗漏的五类钉扎机制；事实核验抓到附录 A 混用 Get-Content 与字节 LF 两种口径（漏掉 HtmlManager.cs 2042 与 FirstWindow.cs 2019 两个超限文件），而标准自己第 2 条就警告过 Get-Content 少算问题。
- **低效**：主会话起草时把侦察报告的"14 个钉扎文件清单"直接当权威写入，未先跑 grep 验证——与 docs 任务"转述失真"是同一教训模式；且首轮统计混用两种口径，说明"自己定的口径自己没执行"。

## 教训 → 具体优化动作

- 涉及"哪些文件被某机制覆盖"的清单，一律内置机器再生成命令（本标准 §2.1 已加行数清单再生成命令），文档中的静态表格仅作快照参考。
- 行数统计一律字节 LF 口径，写文档前用再生成命令出数，不手抄旧数据。
- 对抗审查对"标准/规范类"文档必须包含"遗漏猎手"角色（找机制盲区），仅靠事实核验不够。
- 建议后续（超出本次范围）：为 §6 的四条检查写一个 `tools/` 下的只读汇总脚本（输入目标文件路径，输出命中的钉扎机制清单），把流程纪律工具化。
